# Tests: static consistency (locales and preferences)

Level-1 tests that check the **repository as source** rather than run its behaviour: the locale
files against each other and against the code, and the preference declarations against the code
and the managed layer's validation tables. They scan the tree, so new code is covered as soon as
it is merged, with no test to write.

The contract is the spec, as everywhere in the suite:

- **locales**: [`claude-spec/06-localization.md`](../../claude-spec/06-localization.md), plus
  `CLAUDE.md` rule 2 for `LANG.md`;
- **preferences**: [`claude-spec/05-options.md`](../../claude-spec/05-options.md), `CLAUDE.md`
  rule 7, and [`claude-spec/08-managed-configuration.md`](../../claude-spec/08-managed-configuration.md)
  ("Adding a policy-settable preference", "Content rules", "Policy-supplied API keys").

Each test file names the spec sections it covers in its opening comment. How to run the suite,
the two levels and the known-issue mechanism are in the general [`tests/README.md`](../README.md).
Paths below are relative to `tests/`.

## Running

```sh
node --test "tests/static/*.test.mjs"     # this area only, from the repository root
```

Level 1 only: nothing to install, no jsdom, no network, and nothing is written anywhere. The
area imports only `helpers/core/` (never the managed layer in `helpers/*.mjs`) and has no
plugin, so it runs the same on a branch without the managed area. The whole area takes about a
second: each file is read once per process and its token stream is shared by every check of
the test file that reads it.

## Layout

```
tests/
├── helpers/known-issues/static.mjs  the known issues, their shape (validateKnown()), and
│                                     declareCheck(), which turns a check into tests
└── static/
    ├── source-scan.mjs               the scan: the files, the token stream, argument and
    │                                 literal readers (a helper, not a test: no .test.mjs suffix)
    ├── 01-locales-files.test.mjs     spec 06: the locale files on their own and against en
    ├── 02-locales-references.test.mjs spec 06: the keys the code references, and the unused ones
    ├── 03-prefs-references.test.mjs  rule 7, spec 05: the preference keys the code names
    ├── 04-prefs-defaults.test.mjs    spec 05, spec 08, rule 7: the declarations themselves
    ├── 99-harness-known-issues.test.mjs  the known-issue shape
    └── 99-harness-source-scan.test.mjs   the scan, on small cases and on the real files
```

## The checks

Each check has a name (the first column, also its key in `KNOWN`) and a **subject** per
violation: the thing a known issue names.

| Check | File | Enforces | Spec | Subject |
|---|---|---|---|---|
| `locale-shape` | 01 | every `messages.json` parses; every entry is an object with a string `message`, a name of `[A-Za-z0-9_@]` only, no two names equal ignoring case, a string `description` and `placeholders.*.content` when present | 06 "Message File Format" | `locale` or `locale:key` |
| `en-description` | 01 | every `en` entry has a non-empty `description` | 06 "Message File Format", "Adding a New String" | key |
| `placeholders` | 01 | a translated entry uses the same `$name$` placeholders as `en` | 06 "Golden Rule" | `locale:key` |
| `stale-key` | 01 | a translated locale has no key `en` no longer has | 06 "Golden Rule" | `locale:key` |
| `lang-md` | 01 | every locale `LANG.md` lists exists under `_locales/` (that direction only) | 06 "Supported Languages", rule 2 | locale |
| `missing-key` | 02 | every key referenced from the code exists in `en` | 06 "Using Strings in Code" | key |
| `dead-key` | 02 | every `en` key is referenced from the code | 06 "Adding a New String" (step 4) | key |
| `undeclared-pref` | 03 | every preference key the code reads or writes is in `prefs_default` | rule 7, 05 "Preference access" | key |
| `derivation` | 04 | every `${integration}_${key}` and `${prefix}_${key}` is in `prefs_default` with its generator's default; the global `connection_type` / `use_specific_integration` exist | 05 "Global Integration Settings", "Special Prompt Integration Overrides"; 08 "Adding a policy-settable preference" | key |
| `duplicate` | 04 | `prefs_default` declares each key once: never twice by hand, never by hand over a generated key, never generated by both families | 05 "Settings Structure" | key |
| `orphan-rule` | 04 | every key of `PREF_ENUMS`, `PREF_NUMBER_RANGES`, `CONNECTION_FIELD_ENUMS` is a declared preference (or connection field) | rule 7, 08 "Content rules" | `TABLE.key` |
| `type-coherence` | 04 | a key's default is `''` or a member of its enumeration, or inside its number range | rule 7, 08 "Content rules" | key |
| `secret-name` | 04 | a credential field or preference is named `api_key` / `*_api_key` | rule 7, 08 "Policy-supplied API keys" | key |
| `secret-treatment` | 04 | every `*_api_key` is masked by `mztaManaged._logValue()` and `mztaPrefs._logValue()`, recognised by `isAPIKeyValue()`, and named by every hand-written list of API key fields | 05 "Preference access", 08 "Policy-supplied API keys" | `site:key` |

Two tests per file are reports, not checks: the **unresolvable** keys (02 and 03), built at run
time and listed with their `file:line` as a test diagnostic, never failed. And every file has a
sanity test (the scan found the declarations, the reference forms, the accessor calls), so a
scan that silently finds nothing fails instead of passing.

Message names are compared **ignoring case**, as the WebExtension i18n API does: a reference
spelled `AddTags_…` to a key `addtags_…` works at run time and is not reported.

## What the scan can see

`source-scan.mjs` scans `js/`, `options/`, `pages/`, `popup/`, `api_webchat/`,
`mzta-background.js`, `mzta-background.html` and `manifest.json`; never `tests/`, and never the
vendored code: `js/lib/diff.js`, `pages/_lib/tom-select.base.js`, `pages/_lib/list.js` (List.js,
a webpack bundle) and `api_webchat/markdown-it.min.js`.

JavaScript is read through the core tokenizer (`segments()` in `helpers/core/background-source.mjs`),
so nothing matches inside a comment, and a quote inside a regex literal opens no string. On top
of it, `lex()` makes a token stream, and the checks read call arguments from it:

- a key is **resolved** only when it is a static string: a quoted string, or a template literal
  without `${...}`; in an array, each static element; in an object literal, each plain or
  shorthand property name;
- a variable, a concatenation, a template with `${...}`, a spread or a computed name is
  **unresolvable**: listed, never guessed;
- a template literal without `${...}` whose text contains `i18n.getMessage(` is **injected
  code** (`js/mzta-chatgpt.js` exports the ChatGPT Web content script as one): its body is
  unescaped and scanned as JavaScript too, with the right line numbers;
- a template literal nested inside another's `${...}` is beyond the core tokenizer. The
  real-file test in `99-harness-source-scan` (brackets balance in every file's token stream) is
  what notices a file the tokenizer reads out of step, and it passes on every scanned file today;
- HTML is read as text, with `<!-- comments -->` blanked out. `__MSG_…__` is matched with the
  same pattern `js/mzta-i18n.js` substitutes at run time (`__MSG_(.+?)__`), so a stray
  character in a reference is read exactly as the page would read it.

**Dead keys under-report on purpose.** A key counts as used when any static string in the
scanned code (or an HTML attribute value) equals it, or when it starts with a prefix
(`'prompt_' + id`, `` `prompt_${id}` ``) or ends with a suffix (`id + '_info'`) the code builds
keys from. A key that is only reached through such a pattern is never reported, even if no id
completes it today; in exchange, what *is* reported was checked by hand to appear nowhere.

**Preference keys** are collected from `mztaPrefs.getPref / getPrefs / setPref / setPrefs`, from
`prefs_default.<key>` and `prefs_default['<key>']` (the `get({key: prefs_default.key})` idiom and
its variants, such as `PREFS_INIT_KEYS`), and from a direct `storage.local` / `storage.sync`
`get()` with literal keys. The direct reads skip what spec 05 says is not a preference: a key
with a leading underscore (the large payloads, the migration markers) and
`dynamic_menu_order_alphabet` (`NOT_PREFERENCES` in `03`, which cites the spec).

**The managed layer's tables** (`PREF_ENUMS`, `PREF_NUMBER_RANGES`, `CONNECTION_FIELD_ENUMS`) and
`integration_settings_template` are module-private. They are cut out of the source with
`cutLiteral()` and evaluated with the real exports they use (`valid_connection_types`,
`special_prompts_with_integration`, `featureConnectionTypes()`); nothing is exported for the
test. A renamed table makes `cutLiteral()` throw: the check fails loudly, never passes on
nothing. The duplicate check reads the `prefs_default` literal the same way, since an evaluated
object has already lost its duplicates.

## Adding a static check

1. Name it in `CHECKS` in `helpers/known-issues/static.mjs`.
2. In the test file of its family (or a new `NN-<name>.test.mjs`, opening with the spec section
   it covers), build a `Map` of violations, `{subject: detail}`: the subject is what a known
   issue would name (a key, a locale, `locale:key`), the detail says where.
3. Call `declareCheck('<check>', '<what the spec says>', violations)`.
4. If the scan needs a new reader, add it to `source-scan.mjs` with a case in
   `99-harness-source-scan`. Prefer a reader that under-reports: a noisy static test gets
   ignored.

## Known issues: TODO tests

The general rule is in [`tests/README.md`](../README.md#known-issues-todo-tests). The shape here
is "a check × a subject":

```js
KNOWN = { '<check>': [ { reason: REASONS.x, subjects: ['key_a', 'key_b'] } ] }
```

`declareCheck()` makes three tests of a check:

- `<title>` fails on **any violation `KNOWN` does not list**, at once: a known issue never
  hides a new one;
- `<title> [known: N subject(s)]`, one per group, runs as a node:test TODO while one of its
  subjects still violates (one line per reason, not one per key), and fails as stale once none
  does;
- `<title>: every known issue still reproduces` fails on a listed subject that no longer
  violates, naming it: remove it, so the list only shrinks.

`validateKnown()` (run by `99-harness-known-issues`) refuses a group without a reason, a reason
naming no spec section (`spec NN` or `CLAUDE.md rule N`), a subject that is `'*'` or a pattern,
and a subject listed twice. Today: the `en` entries without a description, the key
`"prefs_reasoning_api_default "` (trailing space) in `en` and the eight translations that copied
it, and the unused `en` keys.

## What is not covered

- **Where a declared preference is read.** Spec 05 says preferences are read through `mztaPrefs`,
  "not with a direct `browser.storage.local.get()`", and lists the deliberate bypasses in prose.
  `03` checks that a directly read key is declared, not that the read is one of the listed
  bypasses: that would mean hardcoding the spec's list of sites here.
- **`.option-input` ids.** The settings pages save every `.option-input` under its id, and the
  feature pages' connection panels deliberately include ids that are not preferences (prompt
  fields, see `js/mzta-prefs.js`). The spec states the other direction only (a preference's
  control is an `.option-input` with its id), which needs the DOM: not checked here.
- **The placeholder definitions.** That a `$name$` a message uses has a `placeholders` entry
  in the same locale is not stated by spec 06, so only the use is compared (`placeholders`).
- **The background's secret handling.** That `get_managed_values` hands pages the marker instead
  of a `*_api_key` is behaviour of `mzta-background.js`, covered by the managed area
  (`tests/managed/05e`). `secret-treatment` covers the masking helpers and the field lists.
- **What a credential is.** Spec 08 and rule 7 say a secret is *named* `*_api_key`, not how to
  recognise one otherwise. `secret-name` uses a word list (token, secret, password, credential,
  bearer, auth, apikey); a bare `key` is not on it, or `chatgpt_prompt_cache_key` (a cache id)
  would be reported.
- **Spec 06's `i18n('key')` and `data-i18n="key"`.** The scan reads both forms, but the code uses
  neither today (`js/mzta-i18n.js` is an object, `i18n.updateDocument()`, that substitutes
  `__MSG_…__`): spec 06 describes forms the code does not have.
- **Number domains other than ranges.** `type-coherence` checks enumerations and the
  `PREF_NUMBER_RANGES` entries; the rules written as code in `prefValueProblem()` and
  `connectionFieldProblem()` (a URL, JSON, a time zone) are not reproduced here. Several defaults
  are deliberately outside them (an empty model or host means "not configured").
